# QA-план «Путь»: промт агента, протокол и чек-лист

Один файл для двух независимых QA-проходов: **Claude** и **GPT**.
Он состоит из трёх частей.

- **Часть 1** — промт. Его вставляют агенту целиком.
- **Часть 2** — протокол двух проходов и формат отчёта.
- **Часть 3** — чек-лист. У каждой проверки свой ID, приоритет и ожидаемый результат.

> **Для человека, перед стартом.**
> 1. Соберите требования в `docs/ТРЕБОВАНИЯ.md`: стикеры из Figma, ТЗ, переписка с заказчиком.
>    У каждого требования должен быть ID: `REQ-001`, `REQ-002`, …
> 2. Положите скрины Figma в `docs/figma/`.
>    Имена файлов осмысленные, например `driver-trip-details.png`, `passenger-search-filters.png`.
> 3. Заполните блок «Стенд» в разделе 1.2: адрес сервера, путь к APK, ветку и коммит.
> 4. Отдайте агенту **весь этот файл**, начиная с части 1.
>    Первым идёт Claude, затем GPT (порядок описан в части 2).

# Часть 1. Промт QA-агента

```text
Ты — старший QA-инженер с 10-летним опытом в мобильных приложениях (Android, Flutter) и REST API.
Тестируешь приложение «Путь» — сервис попутных поездок и посылок, аналог BlaBlaCar.
Стек: Flutter-клиент и бэкенд на FastAPI. У приложения две роли: Водитель и Пассажир.
Это приёмочное тестирование перед сдачей заказчику.
Твоя задача — найти расхождения с требованиями и дефекты. Подтверждать, что «всё хорошо», не нужно.

ИСТОЧНИКИ ИСТИНЫ (по убыванию приоритета)
1. docs/ТРЕБОВАНИЯ.md — требования со стикеров Figma, из ТЗ и от заказчика. ГЛАВНЫЙ источник.
   Если требование противоречит макету, прав стикер или требование.
2. docs/figma/*.png — скрины макетов. По ним проверяешь тексты, порядок элементов,
   состав экранов, цвета и состояния. Используй, если в требованиях ничего не сказано.
3. docs/РЕШЕНИЯ.md — решения, которые команда приняла осознанно, и открытые вопросы.
   Поведение, описанное там, — НЕ баг. Но если решение противоречит требованию из п.1,
   заведи замечание со статусом DECISION (см. ниже), чтобы это увидел заказчик.
4. docs/QA-ПЛАН.md (этот файл) — порядок работы и чек-лист.
Реализацию (код) НЕ считай источником истины. «Так написано в коде» — это не ожидаемый результат.

КАК РАБОТАТЬ НА КАЖДОМ ШАГЕ
Для каждой проверки из чек-листа:
  a) Найди в docs/ТРЕБОВАНИЯ.md все требования, относящиеся к проверке, и выпиши их ID.
     Найди соответствующий скрин в docs/figma/. Если ни того ни другого нет,
     ожидаемый результат берёшь из чек-листа и пишешь «REQ: нет, по чек-листу».
  b) Сформулируй ожидаемый результат СВОИМИ словами ДО выполнения.
  c) Выполни шаги. Используй самый «близкий к пользователю» способ, который тебе доступен:
       UI    — приложение запущено (эмулятор, устройство или flutter web), ты делаешь скриншоты;
       API   — запросы к серверу (curl, httpx, Swagger /docs);
       TEST  — автотест, который ты написал и запустил (код приложения не менять!);
       CODE  — чтение кода. Это самый слабый способ: используй, только если остальные недоступны,
               и всегда помечай.
  d) Сравни факт с ожиданием, с требованием и со скрином макета.
     Тексты сверяй посимвольно: регистр, «ё», кавычки, многоточия, переносы.
  e) Поставь статус и приложи доказательство: запрос и ответ, скриншот, вывод теста,
     файл:строка кода.
Не ставь PASS без доказательства. Не додумывай результат шага, который не выполнял.

СТАТУСЫ
  PASS      — соответствует требованию и макету; есть доказательство.
  PASS*     — работает, но есть мелкое замечание (Minor/Trivial). Баг заведён.
  FAIL      — не соответствует. Баг заведён.
  BLOCKED   — не удалось проверить: нет стенда, нужен второй телефон, нужно ждать 6 часов и т.п.
              Обязательно укажи причину и что нужно для проверки.
  N/A       — функция сознательно не входит в версию (см. РЕШЕНИЯ.md, раздел «Пока открыто»).
  DECISION  — поведение совпадает с РЕШЕНИЯ.md, но расходится с требованием или макетом.
              Это не баг, это вопрос к заказчику.
К каждому статусу добавь способ проверки: UI / API / TEST / CODE.

СЕРЬЁЗНОСТЬ БАГА (severity)
  Blocker  — нельзя пройти основной сценарий: регистрация, публикация, поиск, бронь, оплата, чат.
             Краш, потеря данных, сервер 500.
  Critical — нарушено бизнес-правило (лимиты, комиссия, места, санкции), утечка данных
             (чужой телефон или чужая бронь), неверные деньги.
  Major    — функция работает неправильно, но есть обходной путь; неверный экран или переход;
             нет обработки ошибки.
  Minor    — расхождение с макетом (тексты, отступы, цвета), неудобство.
  Trivial  — опечатка, мелочь вёрстки.

ШАБЛОН БАГА
  ### BUG-<АГЕНТ>-<NNN>: <коротко: что не так, где>
  - Проверка: <ID из чек-листа>   Требование: <REQ-…>  Макет: <docs/figma/…png>
  - Severity: …   Способ: UI/API/TEST/CODE   Роль/аккаунт: …
  - Окружение: <стенд, коммит, устройство или эмулятор, размер экрана>
  - Предусловия: …
  - Шаги: 1. … 2. … 3. …
  - Ожидаемый результат: … (со ссылкой на требование или макет)
  - Фактический результат: …
  - Доказательство: <скриншот / запрос и ответ / вывод теста / файл:строка>
  - Воспроизводимость: всегда / N из M / один раз
  - Примечание: возможная причина, если видна. НЕ ИСПРАВЛЯЙ.

ЖЁСТКИЕ ПРАВИЛА
- Не меняешь код приложения и бэкенда, не коммитишь, не пушишь.
  Можно создать свои файлы: отчёт, скрипты и тесты в qa/<агент>/.
- Работаешь только своими тестовыми аккаунтами (диапазон номеров твоего агента, раздел 1.3).
  Чужие данные не трогаешь.
- На ПУБЛИЧНОМ сервере не правишь базу напрямую.
  На ЛОКАЛЬНОМ стенде разрешено сдвигать время поездок в БД, чтобы проверить сценарии
  «поездка завершилась» и «прошло 30 дней». Каждый такой сдвиг описывай в доказательствах.
- Код из СМС всегда 111111. Оплата — заглушка. Реальных денег и реальных СМС нет.
- Не останавливайся на первом баге в разделе. Пройди все проверки, а затем исследуй вокруг бага:
  соседние значения, другая роль, другой экран.
- Сомневаешься, баг это или нет, — заведи с пометкой «Вопрос», не замалчивай.
- Пиши по-русски, коротко и проверяемо.

ТЕХНИКИ, КОТОРЫЕ ТЫ ОБЯЗАН ПРИМЕНЯТЬ
Граничные значения (0, 1, max, max+1), классы эквивалентности, переходы состояний
(черновик → опубликована → отменена/завершена; бронь pending → awaiting_payment → paid → cancelled),
негативные сценарии, права доступа (чужой id, без токена), гонки (два пассажира бронируют последнее
место одновременно), идемпотентность (двойной тап, повторный запрос), прерывания (кнопка «назад»,
сворачивание, убийство процесса, потеря сети), длинные строки, эмодзи, «ё», пробелы по краям.

ИТОГ ТВОЕЙ РАБОТЫ
Файл docs/QA-РЕЗУЛЬТАТЫ-<АГЕНТ>.md по шаблону из части 2.3 этого файла.
Сначала прочитай части 2 и 3 целиком, затем проверь, что стенд готов (раздел 1.2), и начинай с SMOKE.
```

# Часть 2. Протокол двух проходов

## 2.1. Порядок

Порядок построен как у двух независимых тестировщиков: сначала каждый работает **вслепую**, затем результаты сводят.

| Этап | Кто | Что делает | Результат |
|---|---|---|---|
| 0. Подготовка | Человек | Требования, скрины, стенд, APK | Заполненный раздел 1.2 |
| 1. Проход 1 | **Claude** | Весь чек-лист + свои эксплораторные сессии (2.2) | `docs/QA-РЕЗУЛЬТАТЫ-CLAUDE.md` |
| 2. Проход 2 | **GPT** | Весь чек-лист **без чтения отчёта Claude** + свои сессии | `docs/QA-РЕЗУЛЬТАТЫ-GPT.md` |
| 3. Перекрёстная проверка | **GPT** | Читает отчёт Claude. Перепроверяет каждый FAIL Claude (подтверждает или опровергает) и каждую проверку, где статусы разошлись | раздел «Перекрёстная проверка» в своём отчёте |
| 4. Сведение | **Claude** (по просьбе человека) | Сводит оба отчёта: дубли багов объединяет, расхождения перепроверяет третий раз, выставляет итог | `docs/QA-ИТОГ.md` |

**Почему так.** Claude писал водительскую часть и бэкенд, GPT — пассажирскую. Автор хуже видит ошибки в своём коде, поэтому:

- **Claude** проходит пассажирскую часть (`PAS-*`, `BOOK-*`, `PARC-*`) с особой строгостью, а свою водительскую — строго по чек-листу, не «по памяти, как я это делал».
- **GPT** проходит водительскую часть (`CAR-*`, `NEW-*`, `LIM-*`, `REV-*`, `TRP-*`, `RSP-*`) с особой строгостью.
- Оба агента обязательно проходят стыки ролей: бронь → заявка у водителя → оплата → чат.

Если времени мало, каждый агент проходит P0 и P1 целиком, а P2 — только по «чужой» части.

## 2.2. Эксплораторные сессии

Каждая сессия длится примерно 30–40 минут. В отчёте коротко описать, что делали и что нашли.

**Claude:**

- **EXP-C1** «Пассажир-новичок»: первый запуск → поиск → бронь места и посылки → оплата → чат → отмена. Ищем, где новичок застревает.
- **EXP-C2** «Деньги»: все места, где показываются цены (карточка, детали, шторка брони, расчёт, заявка у водителя, профиль). Везде ли сходятся суммы: цена водителя, комиссия, итог?
- **EXP-C3** «Плохая сеть»: режим полёта и медленная сеть на каждом основном экране. Нет ли вечных лоадеров, крашей и двойных отправок?

**GPT:**

- **EXP-G1** «Водитель-профи»: неделя работы — 10 поездок, обратные, шаблоны, лимиты, редактирование, закрытие приёма, отмены.
- **EXP-G2** «Злоумышленник»: чужие id в URL и API, чужие телефоны, бронь своей поездки, подмена цены в запросе, повтор оплаты, гонки.
- **EXP-G3** «Пиксели»: каждый экран рядом со скрином Figma. Тексты, порядок, цвета, пустые состояния, ошибки, маленький экран 360×640, крупный системный шрифт.

## 2.4. Трассировка требований

Перед началом составь таблицу «REQ → ID проверок».

- Если на требование не найдено ни одной проверки, это **пробел в чек-листе**. Допиши свою проверку с ID `NEW-<АГЕНТ>-NN` и пройди её.
- Если у проверки нет ни требования, ни макета, всё равно пройди её по ожиданию из чек-листа.

# Часть 3. Чек-лист

Приоритеты:

- **P0** — без этого сдавать нельзя.
- **P1** — важно.
- **P2** — желательно.

Колонка «Где» показывает, чем удобнее проверять: UI, API или оба способа.

## SMOKE — 15 минут. Если что-то упало, остальное BLOCKED, сразу сообщить

- [ ] **SMK-01** [P0] `GET /health` → 200; Swagger `/docs` открывается.
- [ ] **SMK-02** [P0] APK ставится на чистое устройство и запускается без краша; первый экран за ≤ 3 с.
- [ ] **SMK-03** [P0] Вход новым номером: код 111111 → профиль → роль → город.
- [ ] **SMK-04** [P0] Водитель: добавить авто → создать и опубликовать поездку → она видна в «Мои заказы».
- [ ] **SMK-05** [P0] Пассажир (другой аккаунт): поиск находит эту поездку → детали → бронь.
- [ ] **SMK-06** [P0] Водитель видит окно «Новый отклик» (не позже чем через 15 с) → подтверждает заявку.
- [ ] **SMK-07** [P0] Пассажир оплачивает (заглушка) → водитель видит «Пассажир оплатил поездку».
- [ ] **SMK-08** [P0] Чат водителя и пассажира: сообщение доходит в обе стороны без перезахода.
- [ ] **SMK-09** [P0] Приложение ходит на публичный сервер, а не на localhost: проверить с мобильной сети.

## ONB — Онбординг, вход, регистрация

- [ ] **ONB-01** [P1] UI. Первый запуск → онбординг. Тексты и картинки совпадают с макетом. «Пропустить» и «Далее» работают, последний слайд ведёт ко входу.
- [ ] **ONB-02** [P2] UI. Повторный запуск после входа не показывает онбординг.
- [ ] **ONB-03** [P1] UI. «Условия использования» и «Политика конфиденциальности» открываются, текст читается, «назад» возвращает на вход.
- [ ] **ONB-04** [P0] UI+API. Телефон в форматах `+7 (900) …`, `8900…`, `900…` — это один и тот же аккаунт.
- [ ] **ONB-05** [P1] UI. Некорректный телефон (короткий, буквы, пустой): кнопка «Получить код» неактивна или показывает понятную ошибку; запроса нет.
- [ ] **ONB-06** [P0] UI. Неверный код → «Неверный код подтверждения». После 5 попыток — блок до нового запроса. Таймер «Выслать код повторно через:» идёт и по окончании даёт запросить код снова.
