## Окружение и инструменты

### `There was an error parsing the body` при curl с кириллицей из Git Bash
Симптом: `curl -d '{"first_name":"Тест"}'` из Git Bash на Windows получает 400, хотя JSON корректен; из тестов и Swagger тот же запрос проходит.
Причина: кириллица в аргументе командной строки уходит не в UTF-8, тело перестаёт быть валидным UTF-8 JSON.
Решение: записать тело в файл (`printf '...' > body.json`) и отправлять `--data-binary @body.json`; либо проверять через `/docs` или pytest.
Проверка: `PATCH /api/v1/me` с телом из файла возвращает 200 и имя на кириллице.
Правило: не считать такой 400 дефектом API, пока запрос не повторён с UTF-8 телом из файла.

### Flutter не открывает `bin/cache/lockfile` внутри sandbox
Симптом: команда завершается сообщением `Flutter failed to open a file at "...\flutter\bin\cache\lockfile"` и просит проверить права на SDK.
Причина: Flutter SDK находится вне разрешённого для записи корня проекта, а CLI обновляет собственный cache/lockfile даже для диагностических команд.
Решение: повторить только нужную команду Flutter с `require_escalated` и узким разрешением; не переносить SDK и не менять системные ACL ради этой ошибки.
Проверка: `flutter doctor -v` или исходная команда завершается без сообщения о `lockfile`.
Правило: ошибку доступа к cache Flutter сначала отличать от дефекта проекта.

### uv не создаёт кеш в `%LOCALAPPDATA%` из sandbox
Симптом: `uv sync` пишет `Failed to initialize cache at ...\AppData\Local\uv\cache` и `Отказано в доступе. (os error 5)`.
Причина: стандартный cache uv находится вне доступного для записи корня репозитория.
Решение: из `backend/` задать `$env:UV_CACHE_DIR = Join-Path (Resolve-Path '..') '.tmp\uv-cache'`, затем повторить `uv sync --dev`; сетевую загрузку при необходимости разрешать отдельно.
Проверка: `uv sync --dev` создаёт/обновляет `backend/.venv`, а `uv run pytest -q` проходит.
Правило: локальный cache держать в игнорируемом `.tmp/`, не исправлять права на `%LOCALAPPDATA%`.

### pytest не создаёт временный каталог вне sandbox
Симптом: тест с `tmp_path` падает с `PermissionError: [WinError 5] Отказано в доступе: 'C:\\Users\\Antony\\AppData\\Local\\Temp\\pytest-of-Antony'`.
Причина: системный `%TEMP%` находится вне разрешённого для записи корня проекта.
Решение: создать `<корень>\.tmp`, перед pytest задать `$env:TEMP=(Resolve-Path '..\.tmp').Path` и `$env:TMP=$env:TEMP`.
Проверка: `python -X utf8 -m pytest -q tests/test_migrations.py` проходит (`1 passed`).
Правило: тестовые временные файлы в sandbox направлять в игнорируемый `.tmp/` проекта.

### PowerShell исполняет Unix `$(...)` из SSH-команды локально
Симптом: удалённый скрипт сообщает `The term 'openssl' is not recognized`, а переданный через stdin путь превращается в `/opt/put/.env\r`.
Причина: PowerShell раскрывает `$()` в двойных кавычках, а строковый pipeline передаёт Windows CRLF в Bash.
Решение: передавать Bash-скрипт literal here-string по stdin и запускать как `tr -d '\r' | bash -s`; секреты генерировать только на сервере.
Проверка: `/opt/put/.env` имеет права `600`, домен длиной 22 символа и два секрета длиной по 64 символа.
Правило: сложные удалённые Bash-команды из PowerShell не вкладывать в двойные кавычки `ssh`.

### `UnicodeDecodeError: 'charmap' codec can't decode byte` при проверке repo-skill
Симптом: `quick_validate.py` падает в `Path.read_text()` на русском UTF-8 файле `.agents/skills/grabli/SKILL.md`.
Причина: Python 3.14.7 в текущей Windows-сессии по умолчанию использует `cp1251`, а валидатор читает файл без явной кодировки.
Решение: запускать валидатор через Python из `backend/.venv` с UTF-8 mode: `backend\.venv\Scripts\python.exe -X utf8 <quick_validate.py> .agents\skills\grabli`.
Проверка: валидатор печатает `Skill is valid!` и завершается с кодом 0.
Правило: для Python-утилит, читающих русские Markdown-файлы без `encoding`, включать `-X utf8`.

### `apply_patch verification failed: ... multiple operations target`
Симптом: патч отклоняется целиком, когда для одного пути одновременно указаны `Delete File` и `Add File`.
Причина: `apply_patch` не допускает несколько файловых операций над одним путём в пределах одного патча, даже если цель — полная замена файла.
Решение: сначала отдельным патчем удалить файл, затем вторым патчем добавить новую версию; остальные изменения применять отдельным независимым патчем.
Проверка: оба последовательных патча завершаются успешно, а итоговый файл содержит новую версию.
Правило: полную замену файла не объединять с другими операциями над тем же путём.

### `flutter.bat` зависает без вывода в exec-сессии
Симптом: `flutter --version`, `flutter analyze` или `dart format` не печатают вывод, а после отмены остаются дочерние `cmd.exe` с высокой загрузкой CPU.
Причина: в текущей Windows exec-среде зависает именно batch-обёртка `flutter.bat`/`dart.bat`; прямой `dart.exe` из того же SDK работает штатно.
Решение: вызывать `bin\cache\dart-sdk\bin\dart.exe`; для Flutter-команд передавать ему `bin\cache\flutter_tools.snapshot` и аргументы `analyze`, `test` или `build`.
Проверка: прямой вызов завершил `flutter analyze`, 7 тестов, web-сборку и `app-debug.apk`; лишних `cmd.exe` не осталось.
Правило: при повторении зависания не запускать новые `.bat` параллельно; сначала завершить осиротевшие процессы, затем использовать прямой entrypoint.

### `dart analyze` не может создать `%LOCALAPPDATA%\.dartServer\.plugin_manager` в sandbox
Симптом: анализ завершается `PathAccessException: Creation failed, path = '...\.dartServer\.plugin_manager'` и `Отказано в доступе`, хотя исходники доступны для чтения.
Причина: analysis server пытается записать служебное состояние в `%LOCALAPPDATA%`, который находится вне разрешённого корня проекта.
Решение: создать игнорируемый каталог `<корень>\.tmp` и перед прямым вызовом `dart.exe analyze` задать `$env:LOCALAPPDATA=(Resolve-Path '.tmp').Path`.
Проверка: `dart analyze mobile/lib/src mobile/test` завершается сообщением `No issues found!` без обращения к профилю пользователя.
Правило: не менять ACL пользовательского профиля ради анализа; служебное состояние направлять в `.tmp/` репозитория.

### `python.exe` из WindowsApps не запускается
Симптом: `python -m http.server` падает с `Program 'python.exe' failed to run` и указывает на `%LOCALAPPDATA%\Microsoft\WindowsApps\python.exe`.
Причина: `python` в `PATH` разрешается в недоступный Windows App Execution Alias, а не в реальный интерпретатор.
Решение: вызывать проверенный `backend\.venv\Scripts\python.exe` по явному пути.
Проверка: Python 3.14.7 запустил локальный HTTP-сервер, все Flutter Web assets отданы с HTTP 200/304.
Правило: не исправлять WindowsApps alias ради проекта, если в репозитории уже есть рабочее venv.

### `Kernel state was reset after inactivity` при первом вызове CUA
Симптом: первое открытие localhost-вкладки после паузы не выполняется и возвращает `Kernel state was reset after inactivity`.
Причина: долго неактивная persistent CUA REPL-сессия уже сброшена, но первый вызов ещё обращается к старому состоянию.
Решение: вызвать `js_reset`, затем повторить инициализацию одним разрешённым API-вызовом, без других действ в том же блоке.
Проверка: после reset вкладка `#/city-selection` открылась, viewport 375×812 применился, скриншот и ввод в поиск сработали.
Правило: после такого сброса не повторять действие на старом handle; все переменные и вкладки получить заново.

## Flutter и Android

### `apkanalyzer` передаёт кириллический путь в `aapt` как `����`
Симптом: `apkanalyzer manifest permissions` падает с `ProcessException`, а в `aapt.exe dump badging` путь к APK содержит `����` вместо имени каталога.
Причина: batch/Java-цепочка Android SDK искажает кириллицу в аргументе пути на Windows.
Решение: временно сопоставить корень репозитория с ASCII-диском через `subst P: "<корень>"` и передать `apkanalyzer` путь `P:\mobile\...\app-release.apk`, затем удалить `subst P: /D`.
Проверка: анализ release APK вывел `android.permission.INTERNET`, camera и location permissions с кодом 0.
Правило: Android CLI-анализ артефактов из кириллического пути выполнять через тот же ASCII-диск, что и Flutter analyze/build.

### `flutter analyze` падает с `FormatException: Unexpected end of input` в кириллическом пути
Симптом: analysis server падает при разборе LSP JSON; в обрезанном сообщении виден URL-кодированный путь `.../%D0%BF%D1%83%D1%82%D1%8C/mobile/`.
Причина: в текущей связке Flutter 3.47.1/Dart 3.13.1 и exec-среды LSP initialization повреждается для абсолютного пути с кириллицей; тот же проект через ASCII-путь анализируется нормально.
Решение: проверить, что буква свободна, временно выполнить `subst P: "<корень репозитория>"`, запустить Flutter-команду из `P:\mobile`, затем удалить сопоставление `subst P: /D`.
Проверка: `flutter analyze` из `P:\mobile` печатает `No issues found!`; `flutter test` и `flutter build web --release` завершаются успешно.
Правило: сопоставление диска временное; не оставлять его после проверки и не переносить репозиторий ради одного запуска analyzer.

### Kotlin plugin падает с `this and base files have different roots` через `subst`
Симптом: Android-сборка через `P:\mobile` падает на Kotlin-плагине с `Could not close incremental caches` и сообщает, что исходники в Pub Cache на `C:` и проект на `P:` имеют разные корни.
Причина: Kotlin incremental compiler пытается сохранить относительные пути между виртуальным диском проекта и реальным диском кеша Flutter-плагина.
Решение: в `mobile/android/gradle.properties` задать `kotlin.incremental=false`; ASCII-диск `P:` по-прежнему использовать из-за кириллицы в исходном пути.
Проверка: `flutter build apk --release` через прямой `dart.exe ... flutter_tools.snapshot` из `P:\mobile` собирает release APK с `image_picker_android`.
Правило: при Android-плагинах не включать Kotlin incremental compilation для сборки через `subst`.

### Android license status остаётся unknown после новой CLI-проверки
Симптом: `flutter doctor -v` показывает `X Android license status unknown`, а `flutter doctor --android-licenses` отвечает `Warning: The --licenses option is no longer needed.`
Причина: установленная Android CLI больше не требует старый режим `sdkmanager --licenses`, но Flutter 3.47.1 ещё не распознаёт этот результат как принятые лицензии.
Решение: не повторять бесконечно `--android-licenses`; проверить реальную сборку `flutter build apk --debug` и обновлять/чинить SDK только если сборка сообщает конкретную ошибку лицензии.
Проверка: проект собирает `mobile/build/app/outputs/flutter-apk/app-debug.apk` несмотря на предупреждение doctor.
Правило: предупреждение doctor не считать блокером без ошибки Gradle или сборки APK.

### Первый web-скриншот показывает пустые места вместо крупных PNG
Симптом: после `networkidle` логотип или иллюстрация отсутствуют на скриншоте, хотя сервер вернул asset с HTTP 200/304 и в консоли нет ошибок.
Причина: Flutter Web завершает сетевую загрузку раньше, чем браузер декодирует PNG и отрисует следующий кадр; воспроизведено на прозрачном `onboarding_car.png` размером около 0,9 МБ.
Решение: сначала проверить запрос asset и console errors, затем дождаться стабильного кадра перед скриншотом; в текущем браузерном QA достаточно дополнительного ожидания примерно 1,5 секунды.
Проверка: повторный скриншот без пересборки показывает логотип и автомобиль на ожидаемых позициях.
Правило: пустой первый кадр не считать ошибкой AssetManifest, пока не проверены HTTP-ответ, консоль и повторный кадр после декодирования.

### Заголовок Flutter bottom sheet переполняется на тестовом шрифте
Симптом: widget-тест на viewport 375×812 сообщает `A RenderFlex overflowed by ... pixels on the bottom` внутри заголовка bottom sheet, хотя сумма отступов и line-height из Figma визуально помещается.
Причина: жёсткая высота контейнера была равна размеру фрейма Figma без запаса на фактические метрики системного шрифта Flutter; высота строки в тестовом renderer оказалась больше расчётной.
Решение: оставить фиксированную высоту самого sheet, но дать его заголовку вертикальный допуск (в текущих компонентах 74 px вместо 59 px), а прокручиваемую середину держать в `Expanded`.
Проверка: `flutter test --plain-name passenger` проходит на viewport 375×812 без RenderFlex overflow.
Правило: размеры фреймов Figma для текста не переносить как предельные constraints без проверки на реальном Flutter font metrics.

### Кнопка «Далее» неактивна при визуально заполненном маршруте
Симптом: все адреса, дата, время и места заполнены, но кнопка перехода остаётся серой.
Причина: `RouteStop.isComplete` требует `city_id`; если города нет в `GET /cities`, текст адреса виден, но остановка не считается валидной.
Решение: добавить город миграцией в серверный справочник; не ослаблять проверку до свободного текста, так как API поездки ожидает `city_id`.
Проверка: миграционный тест находит город, а widget-тест маршрута с этим городом в промежуточной остановке активирует «Далее».
Правило: при таком симптоме сначала сверять каждый город с серверным `GET /cities`.

## Backend

### Docker-сборка падает с `OSError: Readme file does not exist: README.md`
Симптом: `uv sync --frozen --no-dev` в Dockerfile не может собрать локальный пакет до шага `COPY . .`.
Причина: Hatchling проверяет `readme = "README.md"` и пакет `app`, которых ещё нет на раннем слое зависимостей.
Решение: до `COPY . .` выполнять `uv sync --frozen --no-dev --no-install-project`, а после копирования — `uv sync --frozen --no-dev`.
Проверка: образ `put-api` собирается, Alembic доходит до `20261124_0011`, HTTPS health возвращает `200`.
Правило: кэшировать зависимости отдельно от установки самого локального проекта.

### `alembic upgrade head` падает с `table trips already exists`
Симптом: на старой локальной `backend/put.db` миграция `20261122_0001` пытается создать уже существующую таблицу `trips`.
Причина: до перехода на Alembic приложение создавало схему через `Base.metadata.create_all` при старте, таблицы `alembic_version` в такой базе нет.
Решение: если схема совпадает с ревизией 0001, выполнить из `backend/` `uv run alembic stamp 20261122_0001`, затем `uv run alembic upgrade head`; пустую базу можно просто удалить.
Проверка: `uv run alembic current` печатает `20261122_0002 (head)`.
Правило: схему создаёт только Alembic; `create_all` допустим лишь в тестовых фикстурах.

### Время в SQLite сдвигается на величину часового пояса
Симптом: поездка на `09:00+05:00` в локальной SQLite-базе читается как `09:00Z`, сравнения «в будущем / в эти сутки» ошибаются на 5 часов; на PostgreSQL всё верно.
Причина: тип `DateTime(timezone=True)` в SQLite хранит строку без смещения — SQLAlchemy молча отбрасывает `tzinfo`, сохраняя «настенное» время.
Решение: приводить все входящие моменты к UTC до записи и до сравнения (`TripWrite` делает `departure_at.astimezone(UTC)`, границы суток — `.astimezone(UTC)`); при чтении наивные значения считать UTC (`as_utc`).
Проверка: `tests/test_search.py::test_departure_is_stored_in_utc` — 09:00 Екатеринбурга возвращается как `04:00Z`.
Правило: в БД и в SQL-фильтрах только UTC; локальный пояс — лишь для «суток» и отображения.
